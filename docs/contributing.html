Contributing

Everything a new contributor needs that is not obvious from reading the code: why the pieces are arranged the way they are, which constraints are load-bearing, and what is already known to be broken so you do not rediscover it.

Getting set up

git clone https://github.com/shreypatil/coCine
cd coCine
npm install

npm test          # unit + integration, no window, no display
npm run typecheck # three tsconfigs: node, main, renderer
npm run desktop   # build the renderer and launch the app
npm run server    # the signalling server, on :8787

Needs mpv and ffmpeg on PATH. Test films are generated on first run and cached in .fixtures/. npm workspaces, not pnpm — for an environment reason rather than a principled one; switching is a pnpm import away.

Measurement scripts, all pass/fail against the plan's exit criteria:

npm run phase0     # mpv control: event rate, command latency, seek accuracy
npm run phase1     # five clients, drift against the 100 ms budget
npm run phase4     # a swarm fetching a film while it plays
npm run phase7     # relay mode, and what a session costs
npm run nat-check  # what this machine's network does to a peer connection

The one architectural rule

packages/sync touches nothing — no socket, no player, no clock of its own. That is what allows it to be driven against simulated time and adversarial networks with nothing running, and it is why the drift numbers mean anything. Keep it that way.

Decisions, and why

Playback state lives on the server

Not in the host's client. It buys three things: the room survives the host's connection blipping, permissions are enforceable rather than advisory, and a latecomer is correct by construction. The cost is a server that must exist; that was accepted.

Anchors, never commands

playback.schedule carries a position and a server timestamp, never “play now”. Every transition is placed 300 ms in the future so the slowest client can finish its seek before the instant arrives. If you ever find yourself adding a message that tells clients to do something immediately, that is the bug.

Correct by rate, seek only when you must

A seek is always visible; ±5% of speed is not. Under a second of drift is closed by rate over a two-second horizon. The deadband exists because correcting below 12 ms is noise chasing noise.

One MediaTransport interface, two transports

The swarm and the origin fetch differ entirely in mechanism and not at all in shape. Everything above them — readiness, progress, resume, watch-before-complete — is written once. When adding a third, implement the interface rather than special-casing above it.

Two ICE planes, and bulk never gets a relay

iceServersFor('bulk', …) returns STUN only. The enforcement is omission, not a check, so there is nothing to accidentally re-enable. A relayed film costs its operator an 8 GB round trip per viewer.

mpv as a separate process, reparented with --wid

Reimplementing a media player is not a project; driving a real one is. The consequence is the constraint everything visual works around: nothing Chromium draws can appear over the video, because the native surface sits above the page. Controls sit beside and beneath it.

Two follow-on decisions come from that. The surface is reparented into the main window — an Electron non-focusable window is override-redirect, belongs to no workspace, and a tiling window manager leaves it painted over whatever you switch to. And it is only shown once a film is open, which is what lets the empty stage say something useful instead of being a black rectangle.

Fullscreen chat via the X SHAPE extension

Recorded here as impossible for a while. Raising the overlay, lowering the video, setAlwaysOnTop, moveTop, xdotool windowraise and a direct X ConfigureWindow were all tried; the video stayed on top. Alpha does not help either — a compositing manager composites top-level windows, and this one is deliberately a child.

What works is subtraction. The overlay covers the whole video, the renderer measures its message bubbles and reports them, and the main process cuts the window down to exactly those rectangles. No compositing manager required, and input is clipped the same way, so a click outside a bubble reaches the film. apps/desktop/test/overlay-window.e2e.test.ts asserts it against a real X server rather than trusting it.

The overlay never takes the keyboard. It held the composer at first, and every test of it passed: the window appeared, the field rendered, focus was requested. None of that mattered, because a reparented child is not a window any window manager will focus — the field was never typed into and the fullscreen chat could not be used at all. The field is in the main window now ([data-testid="fscompose"], invisible behind the video) and the overlay is sent the draft to draw. The lesson generalises: a test that the interface rendered is not a test that it works.

mpv's video output must survive a resize

This application resizes the window mpv draws into — entering fullscreen, moving the sidebar. mpv's auto-probe order puts sdl before x11, and with vo=sdl a --wid window that is resized goes black permanently: no seek, pause, video-align-y jiggle or filter reconfiguration repaints it. The embedded player is therefore given --vo=gpu-next,gpu,xv,x11 on Linux. COCINE_MPV_ARGS appends arguments after everything else for anyone who needs a different choice, and is how the test suite drives the real output on a virtual display (--gpu-sw=yes) or reproduces the failure (--vo=sdl).

The film picker is ours on Linux

Not a preference — Electron's fallback GTK chooser, used whenever no xdg-desktop-portal is installed, reports an activate gesture to the application as a cancellation:

GestureResult
Double-click a file{ canceled: true, filePaths: [] }
Select, then Enter{ canceled: true, filePaths: [] }
Select, then click Openreturns the path

Reproduced in a twelve-line Electron application, so it is neither this project's code nor its window handling, and it cannot be patched from here. Double-click is how almost everyone picks a file, so “Open film” silently did nothing. Windows and macOS keep their native dialogs; COCINE_NATIVE_DIALOG=1 forces the system one back on Linux.

Electron's window state and X's must be driven together

Reparenting a window unmaps it, so the embed code mapped it back — unconditionally. The video surface is created hidden and belongs hidden until a film is open, so that left a window Electron believed to be hidden sitting mapped over the top-left of the interface: a black rectangle over the launch animation and over the film picker, which nothing corrected because as far as Electron was concerned it was already hidden. X told the story plainly once asked: 

at rest, no film open:
  video surface:  electron.isVisible = false     X.mapState = Viewable

Both windows now go through one setShown() that drives Electron's show/hide and X's map/unmap, and embedWindow maps only what is meant to be seen. video-output.e2e.test.ts asserts the two agree at rest, while playing, and across a picker open and close — and reads the surface's pixels, because every other test passes happily while a film plays with sound and a black rectangle.

Nothing animates in a window that is not on screen

Chromium throttles a hidden window: CSS animations freeze and timers slow to roughly one a second. The launch mark started at React mount, before ready-to-show, so it played to nobody, or froze part-way and thawed late. The main process now reports windowShown in state and the renderer starts nothing before it, with a fallback so a missing state push cannot leave the interface stuck behind a mark that will not finish.

The renderer reports its viewport with the video rectangle

Electron counts a Linux menu bar as part of the window's content while the page's coordinates start below it, so placing the native surface from the page's rectangle alone put the video about thirty pixels too high, over the application's own top bar. The offset is now derived from the reported viewport rather than assumed, and the stock menu is removed on non-macOS platforms.

Opening a film is not sharing it

They were one action, and that made two very different decisions look identical: putting a file on your own screen, and pushing several gigabytes at three other people. Opening now loads the film locally and does nothing else; film:share hashes and announces it; sharing can be paused, which stops serving as well as fetching; and unloading takes it off the room when this machine is the one that put it there. A film cannot be opened outside a room at all — watching alone is not what the application is for, and offering it made the room look optional.

A package built on one platform is not a package for another

This has now broken a Windows installer twice, in two different ways, and both times the application died on launch before a window existed. It is worth understanding properly.

The tree contains two copies of node-datachannel, and they find their native binary by entirely different means:

CopyVersionHow it loads its binary
node_modules/node-datachannel0.33+ requires a sibling package, @node-datachannel/<platform>-<arch>
webrtc-polyfill/node_modules/node-datachannel0.32.3 an unconditional require("../../../build/Release/node_datachannel.node") — no platform packages, no fallback

npm installs only what matches the machine doing the installing, so a Linux build has neither of the Windows binaries. The first failure was the missing sibling package; fixing that exposed the second, the nested copy's missing local build. overrides does not collapse the two — npm ignores it here, silently, however the lockfile is regenerated.

So the build does three things, all in scripts/dist.mjs:

  • fetch-native.mjs stages both binaries for the target under .native/ — the sibling package as a tarball (npm refuses to install one for another platform), the legacy build through prebuild-install, which is exactly what npm would have run on the target machine. It verifies each is the right binary format; a Windows addon that is secretly ELF is worse than none.
  • The sibling package is injected by electron-builder's files from/to. The legacy one cannot be: it lives at a path that already exists in the tree, and the tree's own file wins — which is how a Windows package came to carry a Linux binary at exactly the path Windows looks in. That one is swapped into node_modules for the duration of the build and restored in a finally, because leaving a Windows binary behind would break this machine's tests silently.
  • check-package.mjs then reads the artifact — the archive as well as the directory beside it — and refuses to ship unless every copy of node-datachannel can find a binary by its own mechanism, every binary a loader would choose is built for the target, and nothing native is left packed inside app.asar, which cannot be loaded from.
Two traps worth knowing before you touch electron-builder.yml

node-gyp-build looks in build/Release before prebuilds/<platform>-<arch>, so a locally compiled addon shipped to another platform shadows the correct prebuild sitting right beside it.

A platform's files list replaces the root one, and a list containing only negations has electron-builder prepend the default **/* — which quietly pulled the entire apps/desktop tree, Windows mpv.exe and all, into the Linux package and added 40 MB to it. Repeat the positive patterns in every platform list.

None of this is catchable by testing the source tree: on this machine every binary is present and correct. The bugs existed only inside the artifact, which is why the check reads the artifact.

npm run audit-native answers the obvious next question — what else could do this? It walks the shipped dependency closure (the production dependencies of apps/desktop; the build's own tools never travel) and sorts everything native into three kinds:

KindMeaningIn this tree
portableone package carrying prebuilds for every platform — nothing to do bufferutil, utf-8-validate, utp-native, fs-native-extensions — all four carry win32-x64 and both macOS tuples
siblingsthe binary is a separate package per platform, so the target's must be fetched node-datachannel 0.33
local-buildthe binary lives in the package itself, so a foreign target needs one put there node-datachannel 0.32.3, nested under webrtc-polyfill

It also checks that each portable package really does carry a prebuild for every platform coCine targets — portable is a claim, not a guarantee. dist.mjs runs it before every build and refuses to proceed if a package appears in the last two kinds without being listed in HANDLED. A new dependency that ships per-platform binaries therefore stops the build, rather than shipping an installer that cannot start.

Identity is local, and rooms are anonymous

A stable member id and display name per machine, in userData/identity.json. That covers the whole visible benefit of an account — your name and server are simply there — without an identity provider. Accounts, when they come, are additive; rooms stay invite codes regardless.

Testing, and its rules

Three layers. The first two run on every commit and put nothing on any screen.

LayerCommandWhat it can catch
Unit and integrationnpm test Everything pure, plus the server over a real socket and IPC handlers over injected dependencies.
Renderer in headless Chromiumpart of npm test Real layout. A collapsed video stage, a composer overlapping the panel below, a checkbox stacked above its label — a DOM emulator performs no layout and catches none of these.
Whole applicationnpm run test:app Real Electron, real IPC, real mpv. Opt-in, because some of it needs a display.
Two hard rules

Never put a window on a contributor's desktop. Default tests run under COCINE_HEADLESS=1, which swaps the reparented player for a standalone headless one and leaves the main window hidden. Anything that genuinely needs real windows belongs in an *.e2e.test.ts file, which npm test excludes.

Never drive a GUI with synthetic clicks at guessed coordinates. Select elements through a real automation API. Where behaviour lives outside the page — window stacking, shaping, reparenting — ask X directly, as overlay-window.e2e.test.ts does.

The house style for tests: each one reproduces a bug that actually shipped, and says so in a comment. That is why the assertions look oddly specific — they are regressions, not coverage.

Known issues and limits

The full, candid list is docs/TODO.md. The parts worth knowing before you plan any work:

Not yet proven

  • Two real machines on two real networks. Everything measured so far runs on loopback in one process. NAT traversal between actual hosts, real round-trip variance, and the 10–25% of peer pairs that cannot connect directly are all untested. This is the single largest open item.
  • IPv6 has no coverage, and probably matters more than “loose end” suggests: ICE prioritises it where it exists, and for users on Indian ISPs it is plausibly the biggest determinant of whether peer to peer works at all.
  • The Windows installer has never been run on Windows, and the macOS build has never been made — it needs a Mac.
  • Relay mode has only been proven against MinIO, not Cloudflare R2 itself.
  • TURN credential minting is unverified against a real coturn; the image available for testing has no REST-auth path at all.

Deliberate limits

  • Voice is a mesh, so it stops scaling around eight people, and host mute is advisory — the server carries no audio, so it can only ask. Both need an SFU.
  • Wayland runs under XWayland: mpv cannot reparent into a Wayland surface, so the app forces --ozone-platform=x11. The cost is native fractional scaling.
  • Room state is in memory in one process. Redis becomes necessary with more than one server process; InMemoryRoomStore sits behind an interface so the swap touches nothing else.
  • Relay mode has no quota. Any host in a room on a storage-configured server can upload as often as they like, and the operator pays.
  • Readiness assumes a constant bitrate when converting held bytes into seconds, which is wrong for any real encode. It decides when playback may start, so being approximate costs a slightly early or late gate rather than a wrong picture.
  • Nothing deletes films from the relay bucket; a lifecycle rule is the recommended answer and is a standing cost decision.
  • Chromium's echo canceller cannot hear mpv. No WebRTC setting fixes it; a real fix means routing the film's audio through the same path as the call.
  • No code signing. Windows SmartScreen warns on first install, and macOS cannot auto-update at all until there is a Developer ID certificate.
  • The piece scheduler is not faster than stock WebTorrent. It is kept because it makes streaming-before-complete work, not because it distributes better. Worth re-measuring once real peers with asymmetric uplinks exist.

The one thing blocking public use

An installed copy points at whatever COCINE_DEFAULT_SERVER was set to at build time. Until an instance is running somewhere strangers can reach, a release build has nowhere to point, and the “a friend installs from a link and joins a room” criterion cannot be met however good the installer is. Nothing about this is hard-coded; what is missing is a host.

Working on it

  • Branch off main. Keep the branch to one change.
  • npm test and npm run typecheck must pass. If your change touches native windows, run npm run test:app too.
  • Add the test with the fix, and let it describe the failure it prevents.
  • Comments explain why, not what. The codebase is written that way throughout, and it is what makes the load-bearing constraints survivable — most of the hard-won knowledge in this project is in comments next to the code it constrains.
  • Prefer deleting a special case to adding one. If something needs a special case above the MediaTransport or PlayerController interfaces, the interface is probably wrong.

These docs

Plain static HTML in docs/, served by GitHub Pages straight from the main branch (Settings → Pages → Deploy from a branch → main / /docs). No build step and no second branch, so a change to behaviour and the change to its documentation land in the same commit. .nojekyll is present so nothing is preprocessed.

Edit index.html, using.html, how-it-works.html or this page, and assets/style.css for the shared look. If a number appears on the “How it works” page, it must come from a script in the repository that can reproduce it — no estimates presented as measurements.
