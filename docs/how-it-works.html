How coCine works

Written for someone who has never seen the code and wants to know what is actually happening: what runs where, what crosses the wire, and which of the claims on the front page have been measured rather than assumed.

The shape of the system

Three kinds of process. A desktop application per person, one small signalling server for the room, and mpv — a real media player, driven as a separate process over a JSON IPC socket rather than reimplemented.

Inside the app the split matters: the main process owns the room — the socket, the clock estimate, the sync engine and the transfer — and the renderer is an interface over pushed state, plus the one thing it must own, WebRTC voice, because that is where a microphone and an audio pipeline exist. State is pushed to the renderer ten times a second; every action goes back over a hand-written IPC surface small enough to read in one screen.

Keeping screens in step

The central design decision: nobody is ever told to play now. A command arrives at different clients at different times and therefore cannot produce synchronised playback. Instead the server broadcasts an anchor: 

{ kind: "playing", positionSec: 1240.5, atServerMs: 1765432100300 }

Read as: the film was at 1240.5 s at that instant of server time, and has been advancing in real time since. A client receiving it late is still correct, because it computes where the film should be now. A client receiving it early holds at the position until the instant arrives. Transitions are scheduled 300 ms into the future, which gives the slowest client time to receive the message and finish its seek before the moment it describes.

Three pieces make it hold

Clock offset

NTP-style four-timestamp exchanges every 2 s. The estimate keeps the sample with the lowest round trip rather than an average — that sample queued least in each direction and is the least asymmetric. Averaging folds in every delayed sample's error.

Position extrapolation

mpv reports position at about 25 Hz, so a reading can be 40 ms stale — 40% of the whole budget. Advancing it at the current rate before use costs nothing and removes that error entirely.

Correction by rate

Drift under a second is erased by nudging playback speed by up to ±5% over a two-second horizon, which is inaudible. Only a gap larger than a second earns a seek, because a seek is always visible.

Two mpv details are load-bearing, and both were found by measurement rather than reading: --hr-seek=yes, without which absolute seeks land on the nearest keyframe and can be seconds out; and waiting for playback-restart after a seek, without which time-pos reads stale and the engine corrects against a phantom drift.

A room, from join to play

Room state lives on the server, not in the host's client. That buys three things: the room survives the host's connection blipping, permissions are enforceable rather than advisory, and a latecomer is correct by construction because they receive the current anchor and compute from it.

Permissions are enforced where they cannot be bypassed. A client that has not been given control can send playback.request all it likes; the server refuses it. The interface disables the button as a courtesy, not as the mechanism.

Room codes are the only credential: eight characters from a 27-symbol alphabet with the confusable ones removed (no 0/O, no 1/I/L), about 38 bits, chosen to survive being read aloud.

Moving the film

The film is a BitTorrent swarm, over WebRTC data channels, announced to a tracker the signalling server also runs on the same port. The server will only answer for info hashes a room has actually announced, so it cannot be used as a public tracker.

  1. The sharer hashes the file in chunks — measured at roughly 780 MB/s, so it costs seconds on a large film and needs no worker thread.
  2. The resulting magnet plus piece length goes to the room in media.announce.
  3. Everyone else starts fetching and simultaneously starts serving whatever they have.
  4. Playback reads through WebTorrent's streaming server rather than the file on disk. The file is written sparsely, so reading it directly would return zeros wherever a piece has not arrived; the stream blocks instead and honours byte ranges, so mpv can still seek.

Piece selection runs in three zones — an urgent window just ahead of the playhead, a readahead band after it, and the rest as backfill — which is what makes watching before completion work. Honesty about it: measured against stock WebTorrent in a purpose-built harness, the custom policy was no faster overall, and one naive allocator was twice as slow as doing nothing. It is kept for streaming behaviour, not for throughput.

The readiness gate

Every client reports once a second what it actually has: fraction of the film, contiguous seconds available from the playhead, observed rates, and peer count. The room stays in preparing until everybody holds a lead buffer of 20 seconds, then becomes ready.

The second number is the one that matters. How much of a file exists says nothing about whether it can be played; how long it can play before hitting a hole says exactly that.

The room also computes, and shows:

  • An estimate from observed rates, and the name of whoever it is waiting for. When rates are not yet known it says so rather than inventing a number.
  • Tmin, the Kumar–Ross floor no scheduling policy can beat, so a long wait is explicable rather than just slow.
  • Durability — how many whole copies exist and whether it is safe for the sharer to leave. It counts whole copies rather than per-piece coverage, so a room that collectively holds every piece in fragments still reads as unsafe. Deliberate: a wrong “yes” loses the film.

Relay mode

Peer to peer is the product and it fails for some rooms — nobody able to connect directly, or a sharer whose uplink cannot feed even one viewer. Relay mode is the honest answer rather than a broken swarm: the sharer uploads once to object storage and everyone fetches from there.

Both transports implement one MediaTransport interface, so the readiness gate, progress display, resume-after-crash and watch-before-complete all work identically. The origin path fetches byte ranges where the swarm fetches pieces, ahead of the playhead first and backfilling afterwards.

Clients never hold bucket credentials. The server signs a URL scoped to one method, one key and a few hours. A client cannot name a key either: for an upload the server derives it from the room's own code, and for a download it comes from the room's media — so one room cannot address another's objects. AWS Signature V4 is implemented directly and checked against MinIO in the tests, because a signature that agrees with another copy of the same arithmetic proves nothing.

Voice, and the two ICE planes

Voice is a full WebRTC mesh — one connection per pair, no media through any server. It stops scaling around eight people, where everyone is encoding a separate stream for everyone else. Only one side of each pair offers, whoever has the lexicographically smaller member id, because both offering at once collapses the negotiation.

Roughly one pairing in ten on home connections cannot establish a direct connection; behind carrier-grade NAT, as on most mobile networks, it is most of them. A TURN relay is the way through, and coCine runs one — for voice only.

Why the film is never relayed

A relayed film crosses the relay twice, in and out, for every viewer who needs it — an 8 GB round trip per peer, paid by whoever runs the server. Voice is kilobits and worth relaying; films are not. The enforcement is omission rather than a check: the bulk ICE list contains STUN only, so there is nothing to fall back to.

The visible consequence is worth stating, because it looks like a bug: someone on a hopeless connection will hear everybody perfectly and still fail to receive the film. Relay mode is the answer for that room, and the host has to choose it.

TURN credentials are minted per connection as an HMAC over an expiry timestamp, so no account list exists and nothing needs provisioning. A relay with a fixed password is found and abused by strangers within days, and every relayed byte is billed to its operator.

One limitation with no software fix: Chromium's echo canceller removes only audio Chromium itself played, and mpv plays through an entirely separate path. On speakers, every microphone picks up the film and sends it back. Push-to-talk by default, ducking the film while someone talks, and a headphones hint make it survivable.

Drawing over the picture

mpv is reparented into a frameless native child window kept exactly over the video rectangle, because --wid makes mpv fill whatever window it is given with no way to ask for a sub-rectangle. The cost is absolute: nothing Chromium draws can appear over the video, since the native surface is above the page.

Fullscreen chat therefore needed a second native window above the first — and X11 offers no way to blend one window over another, because a compositing manager composites top-level windows and this one is deliberately a child, so the whole application behaves as a single window on a tiling desktop.

The answer is the X SHAPE extension, from the other direction: rather than making pixels translucent, remove them. The overlay window covers the whole video and is then cut down to exactly the message bubbles the renderer measures and reports, so the film is untouched everywhere else and a click outside a bubble reaches the film. It needs no compositing manager, so a bare i3 session behaves the same as a composited desktop. Windows and macOS use an ordinary transparent window instead.

What happens when things fail

FailureWhat the system does
The socket drops mid-film The interface says reconnecting and rejoins by room code with exponential backoff to 30 s. Chat history and room state come back with the join; playback is the server's and is re-anchored on the next schedule.
The host leaves Hosting passes to whoever has been in the room longest. The room does not end.
The sharer leaves before a second copy exists The transfer stalls. This is why durability is displayed continuously rather than discovered afterwards.
Two peers cannot connect Voice still works through the relay; the film does not move. The room's answer is to switch to relay mode.
mpv is missing A wall, not a banner — with the install command for that specific distribution and a button to copy it. There is no application without a player.
The room empties It is collected after ten minutes of being empty.
